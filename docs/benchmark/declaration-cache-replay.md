# 声明缓存的真实请求回放

先构建 release 引擎与 release 测试程序，并准备当前源码生成的 U-Boot 数据库；样本至少包含 500,000 个声明和 10,000 个文件。

```powershell
cargo build --release -p fossilsense
cargo test --release -p fossilsense --bin fossilsense --no-run
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/benchmark_large_workspace.ps1 `
  -Repeats 1 -IncludeCacheReplay -CaseFilter u-boot-declaration-cache-replay `
  -TimeoutSeconds 120
```

复用指定数据库时可直接执行 `scripts/benchmark_cache_replay.ps1 -Database <db> -Workspace <root>`。聚合脚本会保存源码及样本修订、改动指纹、机器、命令、数据库大小和指标。

每种场景分别执行 64 次生产 Hover 和 64 次定义跳转：冷缓存、预热缓存、刚好能容纳预热集合的容量边界、16 KiB 下的持续淘汰。测试从真实数据库选择 64 个唯一外部函数定义，在单个未保存调用文件中逐一引用它们。被查询的定义文件保持关闭，确保确实经过持久化声明读取和详情缓存；不能以全部来自编辑器 overlay 的结果代替缓存测量。

每次请求验证函数名、源码路径和定义 token 的精确位置，计时覆盖生产 LSP 方法调用全程。报告 P50/P95/P99、缓存命中/未命中、**详情缓存的 SQLite 读取次数**、淘汰数、跳过入缓存数、victim 定位次数、锁等待纳秒及缓存容量。这里的 SQL 指标不包含候选召回或调用关系等其他数据库查询，不能当作整个请求的 SQL 总数。

缓存 `bytes` 包含持有的声明及已分配 map/arena 元数据；两项另有分项统计。删除不会扣减尚未释放的容器容量；请求在缓存之外持有的 Arc 仍由整体进程内存测试覆盖。一次插入最多淘汰 32 条，不足时返回已读取结果并跳过缓存。

此回放记录服务端性能，不代表 VS Code 界面耗时，也不自行设定 Hover 50 ms 门槛。普通补全的 64 次/P95 50 ms/零详情读取及 U-Boot 384/512 MiB 门禁仍需独立通过。只有相同输入、相同场景和完整测量数据才能形成版本前后对比。
